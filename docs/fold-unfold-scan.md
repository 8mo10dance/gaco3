# fold / unfold / scan

## このノートの目的

`fold`、`unfold`、`scan` は、いずれも**状態遷移**を構造化するための考え方である。

- `fold` は、入力列を消費しながら状態を更新し、最後の状態を返す。
- `unfold` は、状態から出力を取り出しながら状態を更新し、出力列を作る。
- `scan` は、`fold` と同じように入力を消費するが、途中の状態をすべて残す。

このノートで扱う `fold` は、入力を左から順に処理する **left fold** である。`fold-right` とは、処理順序や結合の仕方が異なるので区別する。

---

## 1. fold：入力を消費して、最終状態を得る

### 定義

左からの `fold` は、概念的には次の要素を持つ。

- 入力列：`Input` の列
- 初期状態：`State`
- 更新関数：`State × Input → State`

入力を1個ずつ消費し、そのたびに状態を更新する。すべての入力を消費した時点の状態が結果になる。

```text
state₀ --input₁--> state₁ --input₂--> ... --inputₙ--> stateₙ
                                                        └─ fold の結果
```

Scheme では、たとえば次のように書ける。

```scheme
(define (fold-left step init xs)
  (let loop ((state init)
             (xs xs))
    (if (null? xs)
        state
        (loop (step state (car xs))
              (cdr xs)))))
```

### 例：合計

```scheme
(fold-left + 0 '(1 2 3 4))
;; => 10
```

状態遷移を追うと、次のようになる。

| 段階 | 消費する入力 | 更新前の状態 | 更新後の状態 |
|---:|---:|---:|---:|
| 初期 | — | — | 0 |
| 1 | 1 | 0 | 1 |
| 2 | 2 | 1 | 3 |
| 3 | 3 | 3 | 6 |
| 4 | 4 | 6 | 10 |

`fold` の結果は数値に限らない。状態として、リスト、集合、辞書、構文木、複数の値を含むレコードなどを使ってよい。

たとえば、偶数だけを集める処理も `fold` として表せる。

```scheme
(reverse
  (fold-left (lambda (acc x)
               (if (even? x)
                   (cons x acc)
                   acc))
             '()
             '(1 2 3 4)))
;; => (2 4)
```

### 空の入力

入力が空なら、更新は一度も行われない。

```scheme
(fold-left + 0 '())
;; => 0
```

したがって、`fold` における空入力の結果は初期状態である。

---

## 2. unfold：状態から出力列を生成する

### 定義

`unfold` は、seed として与えられた初期状態から、状態遷移を繰り返して出力列を作る。

中心となる要素は次の4つである。

- seed：初期状態
- `stop? : State → Boolean`：生成を止めるか
- `mapper : State → Output`：**現在の状態から、今回何を出力するか**
- `successor : State → State`：**次の状態を何にするか**

概念的な処理は次のようになる。

```text
stop?(state) が真なら終了
そうでなければ
  mapper(state) を出力し、
  successor(state) を次の state として繰り返す
```

Scheme で単純化して書くと、次の形になる。

```scheme
(define (unfold stop? mapper successor seed)
  (let loop ((state seed))
    (if (stop? state)
        '()
        (cons (mapper state)
              (loop (successor state))))))
```

### mapper と successor の違い

`mapper` と `successor` は役割が違う。

- `mapper` は、状態を**観測して出力に変換する**。
- `successor` は、状態を**次の状態へ進める**。

状態そのものを出力するときは両者の違いが見えにくい。しかし、内部状態と出力が異なる例を見ると明確になる。

### 例：1から5までの平方数

内部状態を整数 `n`、出力を `n²` とする。

```scheme
(unfold (lambda (n) (> n 5))
        (lambda (n) (* n n))
        (lambda (n) (+ n 1))
        1)
;; => (1 4 9 16 25)
```

ここでは、

- state：`1, 2, 3, 4, 5, 6`
- output：`1, 4, 9, 16, 25`
- successor：`n ↦ n + 1`

である。`mapper` が平方を計算し、`successor` は整数を1つ進める。出力を変える処理と状態を進める処理は独立している。

## 3. scan：fold の途中状態を残す

### 定義

`scan` は、`fold` と同じ更新関数と初期状態を使いながら、最終状態だけでなく途中の状態も列として返す。

このノートでは、**初期状態を含む scan** を採用する。

```scheme
(define (scan-left step init xs)
  (let loop ((state init)
             (xs xs)
             (states (list init)))
    (if (null? xs)
        (reverse states)
        (let ((next-state (step state (car xs))))
          (loop next-state
                (cdr xs)
                (cons next-state states))))))
```

### 例：累積和

入力が `(1 2 3 4)`、初期状態が `0`、更新関数が加算なら、

```scheme
(fold-left + 0 '(1 2 3 4))
;; => 10

(scan-left + 0 '(1 2 3 4))
;; => (0 1 3 6 10)
```

となる。

```text
入力       1       2       3       4
状態   0 ───→ 1 ───→ 3 ───→ 6 ───→ 10
       ↑                              ↑
   初期状態                       fold の結果

scan の結果: (0 1 3 6 10)
```

`fold` が最後の `10` だけを返すのに対し、`scan` は状態遷移の軌跡全体を返している。

### 空の入力

初期状態を含む定義なので、空入力に対しても状態は1個存在する。

```scheme
(fold-left + 0 '())
;; => 0

(scan-left + 0 '())
;; => (0)
```

## 4. fold / unfold / scan の比較

| 操作 | 出発点 | 状態遷移 | 主な結果 | 入力 `n` 個の場合 |
|---|---|---|---|---:|
| left fold | 初期状態と入力列 | 入力を1個ずつ消費して状態を更新 | 最終状態 | 状態を1個返す |
| unfold | seed | 状態を次々に生成 | 各状態を観測した出力列 | 停止条件による |
| scan | 初期状態と入力列 | fold と同じ更新 | 初期状態を含む全状態 | 状態を `n + 1` 個返す |

三者とも状態遷移を扱うが、何を外から見せるかが異なる。

- `fold`：軌跡を捨て、終点だけを見せる。
- `unfold`：状態を進めながら、各時点の観測値を見せる。
- `scan`：入力消費によって生じる状態の軌跡を見せる。

---

## 5. scan を「fold 的な状態更新を unfold で観測する」と捉える

`scan` の内部状態を次の組と考える。

```text
(accumulator, remaining-input)
```

- `accumulator`：現在までの fold の累積状態
- `remaining-input`：まだ消費していない入力

すると、各役割は次のように分けられる。

- `observe` / `mapper`：現在の `accumulator` を出力する
- `step` / `successor`：次の入力を1個消費し、`accumulator` を更新する
- `stop?`：すべての状態を出力し終えたかを判定する

たとえば累積和なら、概念的な state の列はこうなる。

```text
(0,  (1 2 3 4))
(1,  (2 3 4))
(3,  (3 4))
(6,  (4))
(10, ())
```

これらの state から accumulator だけを観測すれば、

```text
(0 1 3 6 10)
```

が得られる。

この意味で、scan は**fold 的な状態更新を unfold 的に繰り返し観測するもの**と理解できる。

ただし、これは

```text
scan = unfold ∘ fold
```

という単純な関数合成ではない。通常の `fold` を先に実行すると得られるのは最終状態だけであり、途中の状態はすでに捨てられている。最終値 `10` だけから `(0 1 3 6 10)` を一般に復元することはできない。

必要なのは、fold の**結果**を unfold することではなく、fold の**1ステップの更新規則**を、履歴を観測できる状態機械の中で使うことである。

## 6. 境界問題：入力は n 個、状態は n + 1 個

初期状態を含む `scan` では、入力が `n` 個なら状態は `n + 1` 個ある。

```text
入力:    x₁      x₂          xₙ
状態: s₀ → s₁ → s₂ → ... → sₙ
```

ここで、単純な `unfold` の停止条件を

```scheme
(lambda (state)
  (null? (remaining-input state)))
```

とすると問題が起きる。通常の `unfold` は、`stop?` が真になった state には `mapper` を適用しないからである。

累積和の例では、次の終端 state に到着した時点で停止する。

```text
(10, ())
```

したがって `10` は観測されず、結果は誤って

```text
(0 1 3 6)
```

となる。

### なぜ欠けるのか

入力を消費する回数は4回だが、観測したい状態は次の5個だからである。

| state | remaining-input | 出力したい値 |
|---|---|---:|
| 初期 | `(1 2 3 4)` | 0 |
| 1回消費後 | `(2 3 4)` | 1 |
| 2回消費後 | `(3 4)` | 3 |
| 3回消費後 | `(4)` | 6 |
| 4回消費後 | `()` | 10 |

`remaining-input` が空であることは、「更新がもうできない」ことを表す。しかし、それは「現在の状態をもう出力してはいけない」という意味ではない。**遷移の終了**と**観測の終了**を同じ条件にしてしまったことが、欠落の原因である。

### 訂正方法

正しい設計には、代表的に次の2通りがある。

1. 通常の unfold が生成した列の末尾に、終端 state の accumulator を別途追加する。
2. `done?` などの段階を state に持たせ、終端 state を一度観測してから停止する。

2番目の方法を概念的に表すと、次のようになる。

```text
State = (accumulator, remaining-input, emitted-final?)

observe(state) = accumulator

step(state):
  remaining-input が空でなければ
    先頭を消費して accumulator を更新する
  空なら
    emitted-final? を真にする

stop?(state) =
  remaining-input が空 かつ emitted-final? が真
```

これなら `(10, ())` を一度出力した**後**に停止できる。空入力の場合も初期状態だけを出力できる。

具体的な SRFI-1 `unfold` の `tail-gen` を利用した実装は、[Scheme 学習メモ](./scheme-learning-notes.md#unfold-で初期状態を含む-scan-を実装する)で扱う。ここでは、終端を含めるには「停止時の末尾を別途生成する」か「停止を1段階遅らせる」必要がある、という構造を押さえればよい。

## 7. 一般のループを状態遷移として考える

ループを理解・設計するときは、次の4要素に分けると見通しがよくなる。

| 要素 | 問い | 型の例 |
|---|---|---|
| state | 反復を続けるために何を覚えるか | `State` |
| step | 1回で状態をどう変えるか | `State → State` または `State × Input → State` |
| stop? | いつ反復を止めるか | `State → Boolean` |
| observe | 状態のどの部分を外へ見せるか | `State → Output` |

この観点では、fold / unfold / scan は、同じ状態遷移を別々の方法で構造化・観測するものだと捉えられる。

- `fold` は、有限の入力列が反復回数と入力を供給し、最後の state を観測する。
- `unfold` は、state 自身が次の state を生み、各 state から output を観測する。
- `scan` は、fold 型の入力消費を行いながら、初期 state と各更新後の state を観測する。

### 何でも fold と呼べるわけではない

「最終結果だけを返すループ」は fold に似ているが、すべてを自然に有限リストの fold と見なせるわけではない。

たとえば、次のようなループでは「先に存在する有限の入力列を左から消費する」という fold の構造が本質でない場合がある。

- 条件が満たされるまで外部から入力を待つ
- state の内容に応じて次に読む対象が変わる
- 終了するかどうか自体が計算するまで分からない
- 無限列や遅延列を必要な分だけ生成・消費する

一般の `while` は `State → State` と `stop?` を持つ状態機械として表せても、それだけで有限リストに対する fold になるわけではない。「入力列の消費」が自然な構造として存在するかを見る必要がある。

### 副作用・遅延性・停止性

状態遷移として表現するときも、次の点は別に考える必要がある。

- **副作用**：I/O や破壊的更新を含む場合、同じ state から同じ結果になるとは限らず、実行順序も意味を持つ。
- **遅延性**：unfold が無限列を表せても、結果を一度に構築する実装では停止しない。必要な部分だけ評価する仕組みが要る。
- **停止性**：`stop?` がいつか真になる保証がなければ、unfold や一般の状態遷移は終了しない。

状態遷移への分解はこれらの問題を消すものではない。ただし、「何を覚え、どう進み、いつ止まり、何を見せるか」を分離することで、問題の所在を明確にできる。

## 8. 「双対」は逆関数という意味ではない

fold と unfold は、しばしば入力と出力の向きが対照的な操作として説明される。

- fold：列を受け取り、状態へ畳み込む
- unfold：状態から、列を展開する

この対称性を「双対」と表現することはあるが、互いが逆関数だという意味ではない。

fold は通常、途中の情報を捨てる。たとえば複数の異なるリストが同じ合計になるため、合計値から元のリストを一意に復元できない。したがって一般には、fold の結果を unfold すれば元の入力に戻る、とは言えない。

重要なのは逆変換ではなく、

- 入力構造を消費して状態を作る方向
- 状態を進めながら出力構造を作る方向

という構造上の対応である。

## まとめ

```text
fold   : 入力を消費し、最終状態を返す
unfold : 状態を進め、各状態から出力列を作る
scan   : fold の初期状態と途中状態をすべて返す
```

このノートの定義では、

```scheme
(fold-left + 0 '(1 2 3 4))
;; => 10

(scan-left + 0 '(1 2 3 4))
;; => (0 1 3 6 10)
```

であり、空入力なら、

```scheme
(fold-left + 0 '())
;; => 0

(scan-left + 0 '())
;; => (0)
```

となる。

scan を unfold 的に実装するときの核心は、入力 `n` 個に対して状態が `n + 1` 個あることだ。`remaining-input` が空になった瞬間に停止すると、終端状態が観測されない。終端を別途出力するか、停止を1段階遅らせなければならない。

最終的には、fold / unfold / scan を暗記するより、反復を次の4つへ分解できることが重要である。

```text
state：何を覚えるか
step：どう進むか
stop?：いつ止めるか
observe：何を外へ見せるか
```

この分解ができると、単純な集計だけでなく、探索、ストリーム処理、状態機械、複雑なループも同じ視点から整理できる。
